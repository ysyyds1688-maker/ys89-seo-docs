二、目標閉環架構

📊
① 數據層 已完成 90%
GA4 + GSC + Ahrefs + 社群 API(缺) + 註冊數(缺) → D1 → 儀表板 / 自動診斷
▼
🧠
② 診斷 → 任務 缺排程
每日自動診斷 → 產生任務(改標題 / 補內鏈 / 寫新文 / 查下滑)→ 告警板 + TG 推播給 owner
▼
🚦
③ 人審閘門 模式已有 = tg-relay
TG 收到「建議把 X 頁標題改成 Y」→ 按 [批准] / [略過]。這是人唯一要做的事
▼ 批准
🤖
④ 執行層 零件已有
改頁面 = WP-CLI ｜ 寫新文 = /寫文章 skill ｜ 建新站 = /建站 skill
▼
📈
⑤ 驗證層 缺
執行後 7 / 14 天自動回查該頁排名 / CTR / 流量 → 寫回儀表板「行動成效」
⟲ 驗證結果回到 ① 數據層,形成下一圈 — 每一圈 = 數據→診斷→批准→執行→驗證→新數據

三、缺口清單(按優先序)

缺口說明解法規模
G1 社群數據 API同事系統的貼文/曝光/水軍數據進不了儀表板給她 AI 提示詞(已備好,見同資料夾另一檔),產 social-feed.json,collector 接入。對接主鍵 = utm_content 代理碼小
G2 註冊數半自動老闆手動看後台老闆每週匯出 CSV 丟指定位置/TG,AI 自動解析入 D1(儀表板入口已留)小
G3 排程調度器沒有「每天自動跑診斷→產任務」的中樞Claude 雲端排程或 Cloudways cron 跑 CLI;產出寫進告警板 + TG中
G4 執行器+審核閘AI 改站沒有安全迴路復用 tg-relay:診斷產生具體 patch → TG 按鈕 → 批准才跑 WP-CLI中
G5 行動成效追蹤改完沒人回頭看有沒有效D1 加 actions 表(動作/日期/目標頁),7/14 天後自動對比,顯示在團隊視角中
G6 內容閉環「關鍵字缺口 → 新文章」是斷的診斷找非品牌缺口詞 → 自動產 brief → /寫文章 → 排程發佈 → G5 驗證中大
G7 維護監控掛站/SSL/404/外掛出事沒人知(Wordfence 事件風險)collector 加 uptime/SSL/sitemap 檢查,異常進告警板 + TG小
G8 儀表板鎖站公開可寫(註冊數/指派誰都能改)Cloudflare Access email 白名單(等你後台點一次)小
